## Contrato común de escritura del MVP

Comprobante y vista previa: DEV-27 define `SaleSnapshot.Delivery` opcional, `ReceiptDocument(Pdf, Pages)` e `IReceiptRenderer.RenderPreview`/`SaleReceiptService.PreviewAsync`, con lectura del pedido vinculado y permisos de reimpresión. La UI guarda los bytes previsualizados y muestra el diálogo de impresora sobre páginas de alta resolución, sin otra escritura comercial ni migración.

Ampliación autorizada Pedido → POS (20/10/2026, diseño en DEV-17): `ConfirmSale.Order` opcional de tipo `SaleOrderOrigin(OrderId, ExpectedVersion)`, mutuamente excluyente con `QuotationId`. Confirmación comercial y enlace compatible se ejecutan en una transacción del repositorio de ventas, con bloqueo/versionado del pedido antes de cobrar y un único `OperationId`/recibo de venta. WPF no coordina dos escrituras ni genera una segunda venta para recuperar un enlace. Conserva el origen y la solicitud completa ante resultado incierto. No requiere nuevas tablas, procedimientos ni migración; `LinkSaleAsync` continúa para recuperación manual.

Cada solicitud nueva lleva `OperationId` GUID y motivo. Crear el GUID una sola vez al aceptar el usuario la operación y conservar tanto GUID como solicitud completa mientras su resultado sea incierto. `MvpOperationService.FindAsync(guid)` consulta el resultado para el usuario actual. Un reenvío idéntico devuelve el mismo ID; modificar contenido con el mismo GUID da conflicto. Un resultado nulo no prueba que otra conexión haya terminado: conservar la solicitud y reenviar únicamente la misma operación. No generar otra venta/abono por un timeout ni reintentar automáticamente.

`Result<MvpReceipt>` contiene `Id` y `OperationId`. Errores de negocio: `VALIDATION`, `FORBIDDEN`, `INVALID_STATE`, `INSUFFICIENT_STOCK`, `CONCURRENCY_CONFLICT`, `DUPLICATE`. Ante conflicto refrescar y pedir que se revise la información; después crear una solicitud nueva si el usuario confirma una operación distinta. Las consultas pueden lanzar `UnauthorizedAccessException` o `ArgumentException`; errores SQL/transporte desconocidos se diagnostican sin mostrar SQL/credenciales al usuario. Paginación `MvpFilter`: páginas desde 1, tamaño 1–100.

Todos estos contratos están registrados en DI e incorporados a la base de `feature/desarrollo`. Requieren migraciones 012–013; los códigos automáticos requieren además 014. [CI Windows #44](https://github.com/Gust4av033/GoDental/actions/runs/39328112837) aprobó el incremento inicial con 116 casos xUnit, 329 comprobaciones SQL y 101 WPF. La suite `--run-mvp` usa una base aislada y no modifica la base del usuario. Las pantallas operativas se conectaron después en DEV-19/26/27; el recorrido manual en dos estaciones sigue pendiente. DEV-30 resume la validación vigente y los complementos faltantes.

Si vuelve a fallar la preparación del acceso, recoger el tipo de error del registro local sin credenciales y reproducir contra la base de pruebas antes de atribuirlo a lógica.

### Recuperación excepcional · contrato pendiente en feature/desarrollo

`MvpOperationService.FindAsync` sólo distingue resultado confirmado o ausencia. Si una respuesta se pierde y un reenvío se rechaza antes de comprobar el registro (por ejemplo permisos revocados, autorización administrativa o timeout de applock), ese rechazo no demuestra que la solicitud original terminó. La UI conserva GUID/solicitud y no habilita otra escritura equivalente. Se necesita una operación de resolución de estado terminal negativo, bajo el mismo bloqueo transaccional por GUID: entrada OperationId/tipo/hash o solicitud completa, usuario actual; salida CONFIRMADA con recibo, EN_CURSO o RECHAZADA_DEFINITIVA, con error de negocio saneado. Debe comprobar propiedad/permisos y garantizar que una solicitud declarada rechazada ya no pueda confirmarse posteriormente. Sólo entonces la UI podrá liberar o archivar de forma segura una solicitud definitivamente rechazada. Estado: **pendiente**. No se reemplaza `FindAsync` ni se simula una respuesta negativa en UI.
