2. Visión y objetivo del sistema

Construir un sistema de gestión comercial especializado en un depósito de insumos e instrumentos odontológicos en El Salvador. Debe comenzar siendo práctico para una operación pequeña, pero dejar una base sólida para crecer sin rehacer la solución.

Gestionar productos, lotes, vencimientos, existencias y movimientos de inventario.

Gestionar proveedores, compras, importaciones desde China y gastos asociados al costo real.

Gestionar clientes nacionales, cotizaciones, ventas, pagos, crédito y devoluciones.

Permitir que varios usuarios vendan simultáneamente desde distintas computadoras.

Ofrecer reportes, indicadores y recomendaciones comerciales accionables.

Dejar preparada la integración fiscal/DTE de El Salvador sin acoplar la venta al documento fiscal.

Dejar preparada una futura capa de prospección comercial Online, con cumplimiento y revisión humana.

5. Arquitectura y organización de la solución

Arquitectura moderada: suficiente separación para crecer, evitando sobreingeniería.

GoDental.Domain — Entities, Enums, ValueObjects, Rules. Sin dependencias de WPF, Dapper o SQL Server.

GoDental.Application — Interfaces, DTOs, Services, Validators y UseCases. Orquesta reglas y casos de uso.

GoDental.Infrastructure — Data, Repositories, PDF, Fiscal, Importaciones, Online. Implementa acceso externo.

GoDental.Wpf — Views, ViewModels, Navigation, Themes, Controls, Common. Presentación.

GoDental.Worker (futuro) — Tareas programadas/Online cuando deban ejecutarse fuera del ciclo de vida de WPF.

6. Despliegue, multi-PC y concurrencia

El escenario inicial de GoDental tendrá dos laptops con la aplicación y una sola base de datos SQL Server central. Inicialmente una PC principal podrá hospedar SQL Server y ejecutar también GoDental; la segunda laptop se conectará a esa instancia dentro de la red local. El diseño no debe asumir una única estación de trabajo.

Laptop/estación Administrador: puede vender y administrar.

Laptop/estación Vendedor: operaciones comerciales según permisos.

Segunda estación: podrá ser utilizada por otro vendedor o administrador según sesión y permisos.

SQL Server central: única fuente de datos operativos.

En crecimiento futuro, una API ASP.NET Core puede interponerse entre clientes remotos y SQL Server; no se expondrá SQL Server directamente a Internet.

| Concurrencia obligatoriaEl sistema debe asumir que dos usuarios pueden intentar vender, editar o cobrar al mismo tiempo. El stock crítico, correlativos internos y operaciones multi-tabla se protegerán mediante transacciones, validaciones en servidor y control de concurrencia. |

10.3 Lotes y vencimientos

Los productos odontológicos que lo requieran deberán rastrear número de lote, fecha de fabricación, fecha de vencimiento y costo unitario real. El sistema deberá alertar por próximos vencimientos y soportar estrategias de salida/promoción.

10.4 Costo puesto en bodega

La rentabilidad no se calculará únicamente con el precio de compra al proveedor. Se deberán poder distribuir los gastos de importación para obtener un costo real unitario.

10.5 Método de valuación y costo operativo

GoDental utilizará promedio ponderado móvil como criterio operativo de valuación del inventario. Cada recepción actualizará el costo promedio considerando el costo puesto en bodega. Si posteriormente la asesoría contable requiere un tratamiento adicional, éste deberá implementarse sin perder la trazabilidad del costo real por compra/lote.

El costo de entrada debe considerar mercadería, flete/DHL, impuestos/aranceles aplicables, manejo y otros gastos asociados.

La utilidad y margen comercial se calcularán contra el costo operativo real, no únicamente contra el precio unitario del proveedor.

Los costos históricos de compras/recepciones no deben reescribirse al cambiar el costo promedio actual.

10.6 Códigos de barras y etiquetas

El sistema permitirá registrar códigos de barras existentes y generar códigos internos para productos que lo necesiten. La simbología, tamaño de etiqueta y formato de impresión se definirán en INV-01/UX-01. El código deberá ser único cuando se use como identificador operativo de escaneo.

12.5 Formas de pago

Formas iniciales: efectivo, transferencia bancaria, pago por QR, depósito bancario, tarjeta, crédito y pagos mixtos. Una venta podrá dividirse entre varias formas de pago. La integración directa con terminal/procesador de tarjeta queda como integración futura; desde la primera versión debe existir la forma de pago Tarjeta para registrar la operación.

Los métodos de pago serán catálogo/configuración y no valores rígidos en la UI.

Los pagos mixtos deben conservar monto por cada forma de pago y validar que la suma cubra el total correspondiente.

Transferencia, QR y depósito podrán registrar referencia/comprobante cuando aplique.

12.6 Descuentos y autorizaciones

El vendedor podrá aplicar descuentos de hasta 7% sin autorización especial. Los descuentos podrán aplicarse por línea de producto y/o sobre la venta completa. Para impedir eludir los límites, se evaluará también el descuento efectivo total resultante de combinar descuentos de línea y generales.

0%–7%: permitido al vendedor según sus permisos.

Más de 7% y hasta 35%: requiere motivo/justificación obligatoria y registro en bitácora.

Más de 35%: requiere autorización mediante credenciales del Administrador y debe registrar qué administrador autorizó, motivo, fecha y usuario solicitante.

Las contraseñas nunca se almacenan ni registran en la bitácora; sólo se valida la identidad/autorización.

12.7 Devoluciones y cambios

La devolución podrá solicitarse como máximo hasta 1 día después de la compra y requiere factura/comprobante o constancia verificable de que el producto fue adquirido en el negocio. Únicamente un Administrador podrá autorizarla.

Se admiten productos abiertos cuando exista una justificación del defecto/falla y evidencia fotográfica.

La resolución podrá ser devolución en efectivo o crédito/saldo a favor del cliente, según decisión autorizada.

Producto devuelto en condición vendible: puede reingresar a existencia mediante movimiento de devolución.

Producto dañado, defectuoso, contaminado o no vendible: no vuelve al stock disponible; debe quedar identificado como no disponible/cuarentena/daño según el flujo definido en INV-01.

Toda devolución debe enlazarse a la venta original, registrar motivo, evidencia, usuario solicitante y administrador autorizante.

12.8 Listas de precios y reglas comerciales

GoDental soportará múltiples listas/reglas de precio configurables. Como mínimo se prevén precio público/normal, mayorista, clínicas, odontólogos, estudiantes y promocional. Debe ser posible agregar nuevas listas sin modificar código estructural.

El tipo de cliente puede determinar una lista/precio aplicable.

La cantidad comprada puede activar precio por volumen/mayoreo.

El monto de venta podrá intervenir en reglas comerciales cuando el total supere $50.00; este umbral debe quedar configurable.

Las promociones tendrán vigencia y reglas propias; la prioridad exacta entre promociones, listas y descuentos se documentará en VEN-01.

12.9 Crédito y cuentas por cobrar

Podrán recibir crédito las clínicas, odontólogos y clientes mayoristas. La habilitación de crédito, límite monetario y condiciones serán editables por cliente desde una función administrativa. El plazo máximo inicial será de 15 días.

El límite de crédito no se hardcodeará: podrá ajustarse conforme evolucione la operación.

El sistema emitirá avisos/recordatorios de saldo pendiente cada 5 días dentro del flujo de seguimiento.

Se permitirán abonos parciales y múltiples documentos pendientes dentro del límite autorizado.

La regla exacta de bloqueo por mora y las excepciones administrativas quedarán configurables y se cerrarán en VEN-01 antes de implementar crédito en producción.

12.10 Documentos de venta, impresión y comprobantes

El usuario podrá seleccionar el formato operativo aplicable: ticket pequeño tipo POS o documento tamaño carta. También se generarán recibos de pago, estados de cuenta y órdenes de compra cuando corresponda. Mientras no exista integración DTE, los documentos internos deben diferenciarse de un DTE fiscal autorizado.

Impresión inicial: impresora convencional en papel tamaño carta.

El tamaño/plantilla deberá ser configurable para evolucionar posteriormente a formato de factura/ticket térmico sin rehacer la lógica.

Los documentos incluirán logo y condiciones comerciales cuando corresponda.

QuestPDF será la base para PDF/impresión de documentos no fiscales y representaciones permitidas.

18. Reglas de código, Git y base de datos

18.1 Código C#

Clases con una responsabilidad clara.

Interfaces para repositorios/servicios externos donde aporten desacoplamiento.

Async para operaciones de I/O.

SQL parametrizado; nunca concatenar entrada del usuario.

DTOs/ViewModels no sustituyen entidades del dominio.

Validaciones en UI para experiencia y nuevamente en Application/DB cuando protejan integridad.

DI desde el Composition Root; evitar new dispersos para servicios principales.

18.2 Git

main representa código integrable/estable.

Ramas por módulo o mejora importante.

PR antes de integrar cambios relevantes.

No versionar bin/, obj/, .vs/, publish/, logs ni secretos.

Commits con alcance claro.

18.3 SQL Server

Scripts de evolución versionados: 001_Core.sql, 002_Inventory.sql, etc.

PK/FK/constraints explícitos.

Índices definidos por patrones reales de consulta.

Transacciones en operaciones compuestas.

rowversion donde sea útil para edición concurrente.

Fechas almacenadas de forma coherente y convertidas a zona local en presentación según necesidad.

No confiar únicamente en validaciones del cliente WPF para integridad de datos.

18.4 Producción inicial y respaldos

La PC principal de producción utilizará Windows 11 y permanecerá encendida durante la operación. Se dispondrá de OneDrive como destino secundario de respaldo. GoDental debe contemplar respaldo automático diario de SQL Server y documentación de restauración antes de entrar en producción.

No sincronizar los archivos MDF/LDF activos directamente con OneDrive.

Generar primero un backup consistente de SQL Server (.bak) y luego copiar/sincronizar ese archivo a la ubicación de respaldo.

Conservar varias generaciones de backup para evitar que un respaldo corrupto o un error reciente reemplace la única copia útil.

La edición/instancia exacta de SQL Server y la política final de retención se definirán en ARQ-01/DB-01 antes del despliegue.
